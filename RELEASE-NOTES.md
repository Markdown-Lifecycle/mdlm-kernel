# 0.1.1

Process Packages can declare `aws-cdk-deployment@1` and a `deployment` action (ADR-0009, D1). `mdlm deployment run <exact-product> <operation> --stack <slot> --aws-profile apm-<project>` synthesizes the product's CDK app in a networkless, credential-free container, refuses any cloud assembly that would make the host build or run something (executable or Docker assets, symlinks, paths outside the assembly), deploys the validated assembly with the host CDK CLI using only the named APM profile, and writes a write-once receipt with the stack identity, allowlisted outputs, endpoint and a version probe that must return the product commit. A deployment proposal citing that receipt publishes the deployment record with kernel-filled fields. Nothing here has run against AWS yet; no published package offers the capability.

An independent verification activity linked `verified-against` to a passing deployment record now runs in a networked mode (ADR-0009, D2). The verifier joins a per-run internal Docker network whose only way out is a kernel-started proxy that tunnels only to the deployment's endpoint. It receives `MDLM_ENDPOINT` and a per-execution `MDLM_RUN_ID`, and has a fixed 300-second wait. The kernel probes the deployed version before and after the run. A mismatch, including a redeploy during the run, gives outcome `error`. The receipt records the endpoint, version, both probes and the proxy's connection log. Re-reading the stack's last update time is not included yet.

Process Packages declaring `staged-requirements@1` can draft stakeholder requirements first, then add one decomposition group per transaction. Requirement sets may be published and reviewed before every stakeholder root is decomposed, and each set records the kernel-managed `trace_complete`. The named elaboration action may only add one group under an existing requirement, containing every added software requirement and optionally existing shared children, with every earlier requirement and group revision unchanged, so the next review assesses only that group. Implementation publication still requires a complete graph. Packages without the capability keep the existing completeness checks at set publication. Compatible upgrade does not add this capability.

A verification activity may now be published with an `authoring_subject` that is an earlier revision of its action's requirement set, so verification for a passed group can proceed while later groups are elaborated. Every `verifies` target revision and every interface revision those targets use must still be selected unchanged in the current set; otherwise publication names the changed target or interface. `authoring_context` still binds the exact export the verifier used.

A requirement set can adopt a newer interface revision without revising the requirements that cite it. A set candidate's `retargets-interface` link to an exact ICD revision moves every selected requirement bound to an older revision of that agreement onto it, and later sets in the lineage keep it. Review assessment rows include each requirement whose effective interface binding changed, and review context lists them in `interfaceRetargets`. The verification export shows effective bindings; existing activities stay valid against their own authoring set, so a retarget alone needs no activity revision. A requirement revision keeps its predecessor's interface binding for each agreement it does not bind itself. A requirement binding a newer revision than its set's retarget is rejected until the set advances the retarget. Packages opt in with `interface-retarget@1` (Process Package 2.5.44), which compatible upgrade may add.

Review registration and publication, and the review and verification context file exports, now stream the packet instead of building it as one string, so a review context larger than about 512 MiB can be registered and exported. A verifier file shared across commits is read and held once. Digests and exported bytes are unchanged. Standard output without `--output` still builds the whole result.

Verification activity publication now rejects a verifier commit containing symlinks or submodules, or whose source archive exceeds 16 MiB, naming the offending path or the actual archive size. Previously these failed later at adequacy-review export or at every execution. Execution reports an oversized product or verifier source archive as a source-size error instead of an output overflow.

Each accepted publication is now anchored by a kernel-written Git ref, `refs/mdlm/publication/<transaction>`, recording the SHA-256 of every file in its transaction directory. Reads, settlement and replay refuse a transaction whose saved files differ from its anchor. That includes a coordinated edit to an output and its datum, the stored snapshot, package language or proposal digest, and a registered review's subject, inputs or verdict hash, which were previously accepted. An existing repository is anchored on first read from Git history: committed transaction files must match `HEAD`, and never-committed transactions are anchored as found. Carry `refs/mdlm/*` when moving a repository (ADR 0010).

Execution now scans each result before storing its receipt or dry-run cache entry, and refuses one whose captured output, report, artifacts, case results or diagnostic contain an AWS access key ID, an AWS secret access key or session token assignment, an `Authorization:` header with a credential, or a PEM private-key block. The refused result has outcome `error`, lists each match's pattern class, field and byte offset in `secretFindings`, and stores nothing from a matching field. The secret itself is never stored or printed. Receipts stored before this change are not rescanned.

Deployment receipts get the same scan before they are written: synth and host CDK CLI output, stack outputs and the version probe body. A match records outcome `error` with `secretFindings` and removes only the matching values, so the stack identity, exit codes and attempt state remain for teardown.

The default dependency is now Process Package distribution 2.5.48. Its iterative endgame runs non-credit dry runs, using `mdlm execution dry-run` and repeating only the activities a change affects, then a class-wide pre-review, then one for-credit pass on a single frozen version. Every review keeps a finding ledger, has a stakeholder checkpoint with severity classes, and can end in a "stopped with findings" informal verdict. Verification adds screen-truth verdicts, required session and identity risk scenarios, an evidence-size projection and a proportionality floor. It builds on 2.5.47, whose iterative package uses staged requirements and requires this kernel. Fresh `mdlm init --process iterative` products start with stakeholder requirements, then add one reviewed decomposition group at a time. Their requirements start from an operating profile agreed with the stakeholder (callers, faults that matter, trusted platform components, the numbers that matter, the durability level for saved data), with stakeholder-language roots and interfaces that give unusual input only containment outcomes. Every review type shares one severity and stop policy, and verification authors and adequacy reviewers share timing, visibility, checkpoint and dry-run rules. Requirements state outcomes; the author records mechanisms as design decisions in the owning requirement's body, closes provisional requirements before elaborating their branch, and runs a walking skeleton after the roots pass. Requirements review also checks that interface inputs are bounded and that interface clauses can hold together, per-group verification keeps its exported authoring set without a rebind, and a revised interface can be adopted with `retargets-interface` (`interface-retarget@1`). Existing products keep their selected package.

Compatible direct upgrades can opt into `verification-applicability@1` while
preserving existing capability bindings and repository contracts. Unchanged
authenticated VFY retain their exact authoring package and method revision when
all current semantic context matches. New/revised method publication remains
current-package-authored. Pending product review needs fresh target-package
execution/results on the existing IMP; old observations retain their original
packages, bytes and times and cannot become target-package historical evidence.
Current independent review and stakeholder acceptance remain required. This
source change does not select a package for any existing product, change the
default dependency or establish installed qualification/live adoption.

Review context file export now offers explicit `--format shared-verifier-trees` with `--output FILE`. The self-contained archive retains every complete verifier file list, ordered activity occurrence and receipt while storing identical file lists once. `mdlm review expand-context ARCHIVE --output NEW_FILE` restores the full expanded context without lifecycle or source repositories. Default expanded exports and native registration/publication hashes remain unchanged; existing packets keep their recorded identities.

The kernel supports independently correcting an acknowledged error in a failed requirements judgment. Process Packages declaring `review-correction@1` can offer recovery on the same current, unaccepted requirement set. The corrected judgment needs independent reviewer authorship and manager registration, an exact link to the original failure, and a correction reason. Original failure and authority bytes remain history. Current judgments determine the ordinary scoped requirement and decomposition correction frontier; recovery grants no additional stakeholder scope.

The default dependency is Process Package distribution2.5.26 at exact commit `f2e5e45da40a64783ae835bf3c835778fde558ce`. Its iterative package offers this recovery action and requires the new capability, which older kernels reject. Kernel installation alone leaves existing products on their selected package. Compatible `mdlm upgrade` may add this supported service while retaining existing capability bindings, repository contracts and historical data.

Focused source tests and a disposable pricing-history fixture exercised corrected membership allocation, ordinary subsequent correction, preserved history and rejected invalid authority or subjects. These checks used synthetic review transport and do not establish actual independent product judgment, installed release qualification or native product acceptance.

# 0.1.0

The kernel now has an independent release version. Earlier kernel artifacts used version0.0.0 and were identified by source commit and digest. Process Package data moved to the separate private mdlm-process-package repository and distribution2.5.23 without changing package bytes or identities.

`npm ci` installs the exact pinned private Git commit and requires GitHub SSH access. Bare initialization continues selecting mdlm-tiny@1.0.1; named exploratory and iterative initialization remain available. `mdlm init DESTINATION --package DIRECTORY` validates and copies an independently installed package directory.

Existing products continue loading their selected local package. Updating the kernel does not select a new package or rewrite accepted history. The extraction adds no loose ends. Compatible direct products can explicitly preview and apply a newer local Process Package through `mdlm upgrade`, with release notes and before/after work. Immutable transaction and authority history retain their exact authoring packages. Targets must declare compatible migration and retain supported repository contracts; current extracted packages remain fresh-only until a separate compatible release. Package distribution release notes describe package adoption support. Required direct/expression/kernel capability contracts are unchanged, and focused installed tests exercise all three package identities against this kernel release.
