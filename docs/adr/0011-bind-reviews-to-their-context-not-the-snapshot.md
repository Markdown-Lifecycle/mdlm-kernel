# Bind reviews to their context, not the whole snapshot

Review registration and review publication require the proposal's `snapshot` to equal the repository's current snapshot. The snapshot digest covers every lifecycle datum, so any publication between a review's draft and its registration or submission invalidates it with "Review registration package or snapshot changed". This includes an unrelated ICD, activity, result or another review. Only one independent review can be in flight per lifecycle (#1138, measured in the Clinic run on 2026-10-22).

**What a review binds.** A review binds the context it judges: its subject, its inputs and the records the kernel draws from them, plus the exact package (reference, digest and language) and the lifecycle repository identity. That context is the canonical review context, the value `mdlm review context` exports to the reviewer. It already contains the subject and input records, their transitive dependencies the review uses (requirement graphs, interfaces and verified requirements, direct origins, predecessor lineage, accepted baselines, source, verifier source and validated receipts), and the judgments the kernel derives from them, such as earlier reviews of the subject's lineage and verification coverage. The *review binding* is the SHA-256 of `{contract: "mdlm-review-binding@1", repository, context}`, where `context` is the canonical review context without its `snapshot` field, using the same canonical serialization as `contextSha256` ([digests](../contracts/digests.md#review-binding)).

`mdlm proposal draft` writes that value as `reviewBinding` into proposals for `review` actions that require independent review. Other actions, including independently reviewed authoring actions, keep the snapshot rule, because their generated data can depend on records outside the review context. As with the snapshot today, the binding names the context at drafting, so a manager drafts right after exporting the reviewer's context. Registration and submission of a proposal with `reviewBinding` rebuild the context from the current repository and require the same binding, the same package, and that the action is still eligible for the subject with the same inputs. They no longer compare the snapshot. A new registration (`mdlm-registered-review@3`) stores the binding as its `contextSha256`, so submission after other publications still matches it.

So a publication outside a review's bound set leaves its registration valid, and one inside it invalidates it. Inside means anything that changes what the review sees: a new revision of the subject or an input, another review of the subject, a new result or activity an implementation review selects, or a package change.

**Why this keeps the integrity guarantees.** A registration still names the exact context the reviewer judged, the exact verdict bytes and the exact proposal bytes. The snapshot was only a conservative proxy for "the context hasn't changed". Records are immutable revisions, and [ADR 0010](0010-anchor-accepted-publications-outside-saved-copies.md) anchors every byte of every published transaction outside its saved copies. A later publication can't rewrite a bound record. It can only add records. An added record that the review's context selects or derives changes the binding and is refused. An added record that the context doesn't contain can't change what the review judged. Every check that read the current repository still runs at submission against the current repository: eligibility, exact inputs, latest predecessors, fixed links, historical results and the publication lock's final snapshot comparison. The transaction still records the actual pre-publication `snapshot`, and its anchor covers the stored review proof. Repository identity stays in the binding, so a proposal drafted in another repository is still refused.

The binding is only as wide as the context. If a later kernel feeds a review from data the context doesn't carry, it must add that data to the context, or the binding won't see it change.

**Compatibility.** Published transactions with an `mdlm-registered-review@2` proof keep reading, settling and replaying unchanged: settlement checks the stored proof's operation and proposal digest, not its context digest, and ADR 0010 anchors still cover those bytes. A registration made with `@2` before upgrading still authorizes its submission when nothing has been published since, because the kernel recomputes the `@2` context digest (with `snapshot`) for `@2` entries. A proposal without `reviewBinding`, for example one built from `mdlm expectations show` guidance, keeps the whole-snapshot rule. Only drafts written by this kernel get the narrower binding.

**Consequences.** Independent reviews over one lifecycle can register and publish concurrently when their contexts don't overlap. Drafting a review proposal now builds the review context, which costs about as much as an export. `contextSha256` means the binding for `@3` proofs and the full context digest for `@2` proofs.
